# Quant Finance V3.1 严格运行手册

## 生产入口

唯一生产推演入口是 `ScenarioEngine.execute(ScenarioMission)`。Streamlit 的“情景推演任务”页面和 `ScenarioTools.execute_mission(...)` 也只提交该契约。主 facade 上调用旧 `run()` 会直接抛出 `ContractViolation`；迁移测试若仍需旧行为，必须显式导入隔离的 `LegacyScenarioEngine` / `LegacyScenarioTools`，其结果不能作为 PIT、校准概率或组合建议的生产依据。

V3 不会从 `stock_daily` / `index_daily` 推断历史可见性，也不会自动改写截止日、补默认持仓、切换数据源、生成默认 beta、用静态宏观映射制造收益数字，或在报告未原子提交前显示 100%。

## 代码目录与兼容入口

`scenario_engine` 根目录只保留公共 API、`strict_engine.py`、共享异常和 SQLite 事务工具。按职责查找实现：

| 目录 | 职责 |
|---|---|
| `agents/` | 当前模型工具调用、持久化 Agent、依赖检查和模型客户端 |
| `data/`、`events/`、`signals/`、`universe/` | 版本化事实、事件状态、特征与投资范围 |
| `quant/`、`portfolio_policy/` | 条件数值模型、校准与组合约束 |
| `mission/`、`ledger/` | 严格任务执行、状态与账本 |
| `research/` | 共享外部资料读取；旧编排与旧仓库按需加载 |
| `legacy/agents/` | 旧实验的 A2A 消息、角色复核和工作流 |
| `legacy/scenarios/` | 旧情景输入结构、解析、模板与校验 |
| `legacy/data/` | 旧行情接口、历史仓库、知识图谱及连接器 |
| `legacy/simulation/` | 旧回测、压力测试、代理计算、沙盘与递归预测 |
| `legacy/reporting/`、`legacy/monitoring/` | 旧报告导出、评估、权限审计与事件监控 |

`a2a_protocol.py` 仍由旧 `agent_workflow` 调用，现位于 `legacy/agents/`，保留本地消息与任务轨迹，不属于当前生产 Agent 协议。其他旧模块也仍有实验、回放或测试调用，不能仅因不在新链路中就删除。

顶层 `from scenario_engine import ScenarioEngine, LegacyScenarioEngine` 及既有公开报告类型/辅助函数保持可用。内部模块导入使用上述新路径；不再在根目录放置同名转发文件。旧引擎的严格 `execute/deployment_readiness` 继承唯一生产实现，旧 `run()` 仍仅由显式 `LegacyScenarioEngine` 提供。普通生产导入及共享研究读取器不会连带加载旧实验计算栈。

## 启动前必须具备

1. `market_artifacts` 已写入目标组合所需的版本化记录；每条记录的 `payload_hash` 必须与 canonical JSON 的 SHA-256 一致。行情工件还必须显式记录 `frequency` 与 `adjustment`；旧 V3 行情缺任一字段时启动失败并要求审计迁移。
2. `event_ledger` 至少存在一个与当前持仓相关、在任务 `as_of` 已知的 `ObservedEvent`；根事件必须包含结构化 `state_changes`。
3. 至少存在一个结构化 `HypothesisEvent`。没有可量化分支时任务失败，而不是生成自然语言分支后继续给数字。
4. `model_versions` 存在训练截止日在 `as_of` 之前的 `active` 模型；策略必须输出 1/5/20/60 交易日，并登记校准版本。
5. 任务计划要求下列精确 `Domain/Dataset`，同域的其他数据集不能替代：`price/equity_price`、`event/observed_event_source`、`event/event_study_observation`、`event/analog_state_observation`、`fundamental/pit_financials`、`industry/industry_membership`、`flow/money_flow`、`sentiment/event_text_features`、`market_regime/market_regime`、`quant/factor_exposure`、`quant/factor_residuals`、`portfolio_constraint/asset_constraint`、`portfolio/portfolio_snapshot`。
6. `market_artifacts` 中存在 `domain="portfolio"`、`dataset="portfolio_snapshot"`、`entity_id="current"` 的点时组合快照；其现金、数量、价格、权重和总资产必须逐项对账。`portfolio_constraint` 还须为每个持仓提供同一时点的交易约束：T+1 可卖数量、停牌、涨跌停、ST、上市天数、最新价、账户总值和最小交易单位。

任一条件不满足时，系统抛出带稳定错误类型的异常，例如 `DataUnavailable`、`DataConflict`、`PointInTimeViolation`、`InsufficientModelData`、`UncalibratedModel` 或 `InfeasiblePortfolio`。

## 当前持仓识别与快照发布

“情景推演任务”页顶部的“当前持仓智能识别与 V3 快照”是 `CurrentPortfolioSnapshotModule` 的界面投影：

- “持仓来源”可切换为“导入现有持仓”。页面支持券商 CSV/TSV（UTF-8、GB18030、GBK）、模板下载和表格直接粘贴；会自动识别常见中英文字段，将 `SZ000001`、`600000.SH` 等格式归一为 6 位代码，并按数量加权合并重复证券。
- 导入至少要求证券代码、持仓数量和成本价，证券名称可选；账户名称、现金和持仓日期在页面中补充。同名账户默认拒绝写入，只有用户明确勾选覆盖时，才在单个事务内替换该账户的全部持仓。
- 唯一账户或唯一有持仓账户会被自动预选；多个有持仓账户同时存在时必须人工确认，系统不猜测。
- 页面逐只显示数量、成本价、最新可见 V3 估值价、行情日期与行情 Artifact ID。成本价只用于对账展示，不参与快照估值。
- 任一持仓缺 V3 行情时，页面提供腾讯单一来源的“一键获取缺失的严格 V3 行情”，同时保留命令行备选。数量非正整数、成本或行情价格非法、账户现金非法时，发布按钮禁用或发布显式失败。
- “同步账户并发布 current 快照”在一个 `BEGIN IMMEDIATE` 事务中读取账户和持仓、绑定 V3 行情 Artifact、计算总值与权重并写入不可变组合 Artifact；不存在先读后写的并发窗口。
- 页面以账户现金、账户日期、持仓数量/成本/更新时间及最新行情 Artifact ID 计算 `capture_fingerprint`。该指纹与已发布快照不一致时，“一键开始完整推演”保持禁用，防止旧持仓被误称为当前持仓。
- `account`/`positions` 均为空时，页面会明确报告“没有可识别持仓”。系统不会从 Agent CSV 日志、`stock_daily`、成本价或默认标的推断当前组合。

首次建立模拟账户及录入真实数量可使用：

```powershell
python main.py create-account 我的组合 --capital 1000000
python main.py load-account 我的组合
```

快照只解决组合引用；事件、财务、行业、资金流、情绪、因子、交易约束和校准模型仍须分别满足启动条件。

持仓快照发布后，用户必须先输入本次真实任务目标，页面才运行只读部署检查。旧实现用“推演前数据准备检查”这个占位任务提前检查事件，无法判断事件相关性，现已删除。检查按“数据集/路由、逐标的覆盖、事实事件、假设分支、校准模型”展示待处理项及获取方式，并可下载本次检查的审计 JSON。检查失败不会创建任务，也不会用默认数据绕过。

当持仓状态日期等于任务日期时，页面会要求用户按券商页面确认每只证券的“可卖数量”。该值写入 `scenario_position_operational_state`，来源标记为 `user_confirmation`；未确认时 `asset_constraint` 保持阻断。跨日持仓才可按 A 股 T+1 规则把当前数量作为可卖数量，系统不会对当日导入持仓做同样假设。

## 数据源部署

统一配置模板为项目根目录 `.env.example`。复制为 `.env` 后填写真实值；`.env` 已被 Git 忽略。模板明确列出：

- `SCENARIO_LLM_API_BASE` / `SCENARIO_LLM_API_KEY` / `SCENARIO_LLM_MODEL`
- `TUSHARE_TOKEN` 与 `STOCKM1_TUSHARE_ENABLED`
- 公共源启用、LLM 请求超时以及模型校准闸门

当前公共链路实际验证的依赖锁在 `requirements-scenario-public.txt`；核心 `requirements.txt` 不假装包含付费数据权限。安装后先执行：

```powershell
python main.py scenario-doctor
python main.py scenario-doctor --live-llm
```

第一条只报告本地依赖和配置，不把“能读取 key”写成“API 可用”；第二条会产生一次少量模型用量，只有真实 `chat.completions` 返回非空 JSON 才标记通过。严格数值引擎仍使用 `use_llm=False`：页面单独调用 `ScenarioLLMClient` 做自然语言结构化，并展示实际主机、模型、用量和错误；大模型输出不进入收益率、概率、CVaR 或目标价生成边界。

TuShare Pro 和 AKShare 均为延迟导入的可选 Adapter。不要把 SDK 加回核心 `requirements.txt`。每个生产环境应根据真实许可证、地域、字段权限和契约 fixture 生成自己的精确 lock 文件；未经逐数据集 canary 验证的 SDK 版本不得标记为 `available`。Adapter 构造器接收数据集专用 row fetcher、normalizer 和 probe，不能用一次账号探测把所有数据集整体标记可用。

页面和 CLI 已提供逐组件公共采集。必须显式确认研究用途和上游条款；任何组件失败只报告该组件，不静默换源：

```powershell
python main.py prepare-scenario-public-data --symbol 002230 --ack-public-research-terms
python main.py prepare-scenario-public-data --symbol 002230 --include-money-flow --ack-public-research-terms
```

第一条调用已验证的 AKShare 财务摘要、巨潮行业变更/公司概况和个股新闻端点，写入 `pit_financials`、`industry_membership`、`observed_event_source` 与版本化 `event_text_features`。财务摘要不提供公告时间，因此 `published_at` 保持 `NULL`，历史记录只从实际 ingestion `known_at` 起可用；总资产和总负债如由披露权益与资产负债率计算，会在 payload 中保存公式与输入。行业端点同时返回多套分类标准，系统按明示策略选择一套当前标准并记录候选数，不把并行分类伪造成连续变更。新闻只保存上游返回的标题、摘要、来源、链接和文档哈希，不冒充全文。

第二条另取同花顺个股资金流全表。该接口实测可能耗时 1–2 分钟，因此在页面中是独立慢速按钮；同代码分页重复只有在标准化数值完全一致时才去重，否则失败。中文“万/亿”和百分比会转为 CNY/小数并保留源快照类型。

公开数据完成后，可从已记录的真实 V3 工件派生市场状态、因子、残差与约束：

```powershell
python main.py derive-scenario-features --symbol 002230
python main.py confirm-sellable --account-id 2 --symbol 002230 --as-of-date 2026-08-17 --position-quantity 10 --sellable-quantity 10
```

市场状态使用等权 A 股收益、20 日趋势/波动、量能比、广度和 60 日市场相关性；因子暴露为实际日对数收益对等权市场收益的 OLS beta，残差样本为真实 1/5/20/60 日滚动残差和。每条工件保存计算窗口、样本量、公式和输入工件摘要。交易约束使用真实持仓数量、用户确认/跨日可卖数量、最新/昨收行情、上市日期、ST/停牌/涨跌停规则、20 日成交额代理和财务/行业工件。缺任一输入时只报告失败。

这些公共入口不能凭空生成成熟的历史事件研究数据。`event_study_observation` 和 `analog_state_observation` 必须有真实公告/事件日期以及已经成熟的 1/5/20/60 日后验收益；只有取得有权限的 TuShare 或导入自有可审计事件数据后，才能做留出样本覆盖率和 CVaR 校准。`model_versions` 只有校准指标实际通过闸门时才能登记 `active`。近期新闻不足 60 日、GDELT 返回 429 或全市场业绩历史端点超时，都只能保持阻断，不能用报告期末、默认样本或手填漂亮指标代替。

页面“历史事件样本与真实校准”区域提供 CSV 模板、上传预览、成熟度检查和校准按钮；CLI 等价入口为：

```powershell
python main.py import-scenario-events --file .\历史事件.csv --symbol 002230
python main.py calibrate-scenario-model --event-type financing --symbol 002230 --min-samples 20
```

事件 CSV 必须提供唯一事件 ID、事件类型、关联证券、带时区的实际发布时间、标题、可核验原文/完整摘要、来源 URI、非空 `state_json` 和用户声明的许可标签。导入器计算原文 SHA-256，并用“事件时刻之前最近收盘价”及其后第 1/5/20/60 个交易日收盘价生成实际对数收益；后续交易日不足 60 时该行失败，不接受 CSV 直接填收益。

校准器按事件时间顺序保留末段事件做样本外验证，训练分布的 10%–90% 区间目标覆盖率为 80%，同时计算验证结果跌破训练 q10 的下尾超限率。指标和源工件摘要写入 `model_versions`；超过 `.env` 闸门时状态为 `rejected`，只有同时通过才是 `active`。任务计划会读取 active 模型的 `adapter_weights`：未登记模型时仍检查 event-study、factor、analog 全集；登记事件/相似状态模型后只要求它实际声明的量化数据，不再误报未使用的 factor 数据。

三种日行情统一经过 `normalize_daily_price_rows`：TuShare 的手/千元转换成股/元，AKShare 和腾讯的成交量从手转换成股。腾讯 `appstock` 当前的 6 字段历史日线不提供成交额；除权除息日的第 7 项是公司行动对象，不是成交额。工件将 `amount` 保存为 `null` 并记录 `amount_not_provided_by_source`，公司行动原样收录到 `source_metadata`；禁止填 0 或估算。外部历史响应的 `known_at` 等于真实入库时刻，不会回填成历史交易日；因此今天第一次抓到的历史记录只能服务截止时点不早于本次入库的任务。

腾讯行情的严格 V3 入库命令如下。`--end-date` 必须显式指定已收盘交易日；盘中当日日线会因 `event_time=15:00` 晚于真实入库时刻而失败，不会被悄然丢弃或作为收盘价使用。

```powershell
python main.py ingest-v3-prices --symbol 000001 --start-date 20240801 --end-date 20260813
```

不传 `--symbol` 时将处理 `stock_info` 中的全部标的；默认按 `market_artifacts` 中腾讯 V3 工件的最新交易日增量下载。该命令不会导入或改写 legacy `stock_daily`。普通 `download-stocks` 命令可用 `--source tencent_http` 显式选腾讯，但它仍属于 legacy 交易模拟数据路径，不足以解除 V3 就绪阻断。

全市场批量时，腾讯成功响应但某标的在增量区间内无日线，会记录为类型化覆盖缺口。已有 V3 历史工件的退市、停牌或无新交易标的会明确跳过，不中止其他标的；从未在请求区间出现过记录的标的会记为失败，全批结束后命令返回非零。审计详情原子写入 `data/v3_tencent_ingestion_audit.json`。网络、JSON、schema、单位或入库错误仍立即中止，不会被按覆盖缺口吞掉。

跨源故障切换只有 `RoutingRule.allow_audited_failover=True` 时才允许，并且前后来源的口径、复权、币种、单位、时间戳、修订与许可范围必须在部署策略中证明兼容；结果显式记录 `audited_failover_used` 和失败来源。默认规则不切换来源。

## 持久化与进度

以下产物由同一个 SQLite 运行账本管理：

- `scenario_missions` / `scenario_mission_steps`
- `scenario_progress_events`
- `scenario_branch_specs`
- `feature_snapshots`
- `scenario_loss_cube`
- `portfolio_proposals` / `portfolio_proposal_comparisons`
- `validation_results`
- `scenario_run_bundles`
- `scenario_execution_jobs`
- `scenario_retry_jobs`
- `scenario_monitoring_jobs`
- `scenario_observed_event_tasks`

根情景和每个分支都必须生成不同的 `feature_snapshots`，且特征快照 ID 进入所有数值结果的 provenance。最终完成进度事件、分支监控任务、run bundle 和 `SAVED` 状态在同一事务中提交；事务失败时页面不能出现 100%。执行 Worker 和监控 Worker 均使用独占租约与持续心跳；进程中断后只允许认领已过期租约，旧 attempt 明确记为 `worker_lease_expired`，新 attempt 使用关联的新 run ID，不覆盖旧审计。没有真实 `next_check_at` 时不猜测轮询间隔。

任务失败状态必须区分 `DEGRADED`、`RETRY_SCHEDULED`、`INSUFFICIENT_DATA`、`REJECTED_BY_CRITIC` 和 `FAILED`。只有提供方给出带时区的明确重试时点时才创建 `scenario_retry_jobs`。

组合方案由 `scipy.optimize.milp` 的 HiGHS 后端求解整数交易手数、CVaR、最差分支、换手、成本、现金、行业、集中度、T+1、停牌/涨跌停和流动性约束。只接受 solver status 为 proven optimum 的结果；不可行返回 `InfeasiblePortfolio`，超时或非最优终止返回 `OptimizationFailure`，不做四舍五入或启发式补解。
