# StockM1 情景推演引擎改进方案

> 文档目的：评估 `Docs/forward_looking_evolution_plan.md` 中“路线 F：情景推演引擎（What-If Scenario Engine）”的技术可行性、商业价值与产品化落地方案，并给出可直接指导开发的细化设计。  
> 适用系统：StockM1 / IGE A 股智能投顾实验平台。  
> 推荐开发模式：PDD + TDD 混合。先用 PDD 固化产品场景、输出契约和合规边界，再用 TDD 锁定每个可计算模块的行为。

---

## 一、结论

路线 F 是一个有技术可行性、真实商业需求和产品差异化潜力的方向，但原方案需要从“LLM 直接回答假设问题”升级为“LLM 编排 + 结构化场景 + 因子/事件/组合模型校验 + 可审计报告”的金融压力测试产品。

### 1.1 是否可行

可行，原因如下：

1. StockM1 现有系统已经具备基础设施：SQLite 日线行情、指数数据、持仓/交易记录、模拟交易引擎、Function Calling 工具、Streamlit 可视化、严格时间防泄露机制。
2. 情景推演本质不是预测单一价格，而是把“事件冲击”映射为“风险因子、行业、个股、组合”的多路径影响，这可以在当前日线数据和模拟账户之上增量实现。
3. LLM 的优势适合承担场景解析、因果链枚举、历史类比检索、报告解释、反方观点生成；不适合单独承担数值收益率预测。
4. 多个业内产品公开展示了“历史情景、假设情景、组合压力测试、what-if 分析”能力，说明这类功能是机构风险管理和投顾沟通中的真实需求。BlackRock Aladdin、MSCI BarraOne、Bloomberg PORT、FactSet、Vanguard 等产品均公开展示了压力测试、情景分析或 what-if 分析能力。

### 1.2 是否有商业实际用途

有。更准确地说，它比“普通 AI 股票问答”更接近专业投研、风险管理和投顾沟通中的付费工作流，但具体商业化能力仍取决于数据质量、合规边界、报告可信度和实际回测表现。

对个人投资者，它回答的是“我持仓会受什么影响、要不要调仓、风险暴露在哪里”。  
对投顾和私募，它回答的是“客户组合或策略在宏观、政策、行业事件下会怎样、该如何解释风险、如何形成投资委员会材料”。  
对教学和研究，它提供一个可复现实验平台，用于比较 LLM 推理、历史事件研究和传统压力测试方法。

### 1.3 是否是非常好的思路

是，但成立条件是保持金融产品的真实边界：

- 不能承诺“预测明天涨跌”。
- 不能让 LLM 编造概率和涨跌幅。
- 必须区分“事实数据、模型估计、LLM 推理、人工假设”。
- 必须输出置信度、证据来源、敏感性、反向风险和不可知项。
- 必须能回测：历史上某日只使用当时可见数据，问系统“如果发生某事件”，看后续真实路径是否落在推演区间内。

因此，路线 F 最适合定位为：**持仓级情景压力测试与投资认知辅助引擎**，而不是自动交易信号生成器。

## 二、外部前沿与产品参照

### 2.1 成熟商业产品显示需求真实

1. BlackRock Aladdin / Aladdin Wealth  
   官方资料强调可对历史事件和假设事件做组合压力测试，支持对股票、利率、信用利差、商品、汇率等因子施加冲击，并用当前组合暴露评估影响。  
   参考：`https://www.blackrock.com/aladdin/products/aladdin-wealth/insights/power-of-stress-testing`

2. MSCI BarraOne  
   BarraOne 提供多资产风险模型、VaR、全重估压力测试、用户自定义历史/假设情景和 what-if 分析，强调持仓级、因子级、交易前决策支持。  
   参考：`https://www.msci.com/data-and-analytics/portfolio-management/barra-one`

3. Bloomberg PORT  
   Bloomberg PORT 支持自定义历史或假设情景来压力测试组合，例如用历史事件行为构建自定义场景。  
   参考：`https://www.bloomberg.com/professional/insights/trading/how-to-build-custom-scenarios-to-stress-test-your-portfolio/`

4. FactSet Portfolio Analysis  
   FactSet 在关税环境中提供主题压力测试，使用历史上类似关税事件的观察响应，评估行业指数、国家指数、汇率等影响。  
   参考：`https://insight.factset.com/portfolio-scenario-analysis-and-stress-testing-in-tariff-conditions`

5. Vanguard Advisor Portfolio Stress Testing  
   面向投顾使用历史市场事件和假设冲击，帮助识别组合脆弱点、比较组合、形成客户沟通报告。  
   参考：`https://advisors.vanguard.com/strategies/portfolio-strategies/portfolio-analytics/stress-testing`

结论：路线 F 的商业需求不是臆想，市场上已有成熟产品把“情景压力测试”用于专业投研和投顾流程。StockM1 的差异化不是第一个做压力测试，而是把 A 股场景、自然语言假设、LLM 辅助因果推理、个人持仓解释和可回测沙盒结合起来。

### 2.2 前沿研究给出的技术方向

1. LLM 金融市场仿真与多智能体市场  
   ASFM、TwinMarket、StockSim、MarS 等研究说明：LLM Agent 和生成式模型可以用于金融市场仿真、行为建模、订单级模拟或多主体互动实验。它们对 StockM1 的启发是：LLM 可以参与叙事、行为和决策过程建模，但价格路径、组合损失和交易约束仍应由订单簿、因子模型、历史数据或规则引擎等可校验模块支撑；这一点是从这些系统设计中得到的工程推论，而不是所有论文都直接给出的结论。  
   参考：  
   `https://huggingface.co/papers/2406.19966`  
   `https://huggingface.co/papers/2502.01506`  
   `https://arxiv.org/abs/2507.09255`  
   `https://www.microsoft.com/en-us/research/publication/mars-a-financial-market-simulation-engine-powered-by-generative-foundation-model/`

2. LLM 反事实与压力场景生成  
   近年的 LLM 金融推理研究开始讨论把 LLM 用于组合优化约束、场景化压力测试、合规分析和信用风险等任务。本文档采用的保守工程原则是：LLM 负责生成可读、结构化、可审计的场景与推理链，损失估计仍由因子映射、VaR/ES、事件研究或组合模型承担。  
   参考：`https://papers.ssrn.com/sol3/papers.cfm?abstract_id=5048316`

3. 多场景与反向压力测试  
   ECB/BoE 相关研究强调多场景压力测试和 reverse stress testing，即寻找能把银行或组合推向最坏结果的一组宏观金融风险因子。  
   参考：`https://papers.ssrn.com/sol3/papers.cfm?abstract_id=4830237`

4. 因果压力测试  
   金融压力测试不能只依赖相关性，应该用因果网络或结构化假设表达“事件如何传导”。这与路线 F 的“多路径推演”高度一致。  
   参考：`https://www.sciencedirect.com/science/article/pii/S1877750317311377`

5. 结构化输出与工具编排  
   情景引擎应使用 JSON Schema / Pydantic 等结构化输出约束，防止 LLM 省略字段或随意编造格式。OpenAI Structured Outputs、LangGraph、MCP、LlamaIndex Property Graph 等框架或协议可作为工程参考，但是否引入要服从当前系统复杂度。  
   参考：  
   `https://openai.com/index/introducing-structured-outputs-in-the-api/`  
   `https://docs.langchain.com/oss/javascript/langgraph`  
   `https://modelcontextprotocol.io/docs/learn/server-concepts`  
   `https://docs.llamaindex.ai/en/stable/api_reference/indices/property_graph/`

### 2.3 可用于开发的前沿方法与框架审查

本节只列入对 StockM1 情景推演引擎有实际工程价值的方法。结论不是“全部采用”，而是按阶段选择，避免为了追逐框架而牺牲系统可解释性和可维护性。

#### 2.3.1 Agent 编排框架

1. LangGraph  
   适合 V1 以后引入。LangGraph 的价值在于显式状态图、checkpoint、持久化、可恢复执行、人类确认节点和轨迹审计。情景推演天然需要“解析 -> 证据 -> 计算 -> 多 Agent 审查 -> 校验 -> 报告”的有向流程，且金融场景需要可追踪、可暂停、可复跑，因此 LangGraph 是最契合的生产级编排候选。  
   不建议在 MVP 一开始就引入完整 LangGraph，因为当前项目代码体量较小，先用普通 Python pipeline 更容易验证核心算法。等出现多 Agent 分支、人工确认、长任务恢复、审计追踪需求后再迁移。  
   参考：`https://docs.langchain.com/oss/python/langgraph/persistence`、`https://docs.langchain.com/oss/python/langgraph/durable-execution`

2. Microsoft Agent Framework / AutoGen 后继路线  
   Microsoft Agent Framework 是 Semantic Kernel 与 AutoGen 团队的新一代 Agent 框架，强调多 Agent、工作流、状态管理、类型安全、遥测和 human-in-the-loop。它值得持续关注，尤其适合未来 Azure 生态或企业客户部署。  
   但截至本文档审查时，官方文档标注为 public preview，不建议作为 StockM1 第一版核心依赖。可以借鉴其“显式 workflow + durable task + telemetry”的思想。  
   参考：`https://learn.microsoft.com/en-us/agent-framework/overview/`

3. CrewAI  
   CrewAI 的 Crews/Flows 模型适合快速搭建角色型 Agent 团队，例如 Bull、Bear、Risk、Policy、Quant 分工。它适合做概念验证或研究 demo。  
   对 StockM1 的限制是：金融压力测试需要确定性流程、严格审计、数值来源校验和失败恢复；这些需求更偏向显式工作流。CrewAI 可以作为原型工具，但不应在未充分测试前承担核心压力测试链路。  
   参考：`https://docs.crewai.com/introduction`

4. OpenAI Agents SDK / Responses API  
   如果未来从 Qwen/OpenAI-compatible Chat Completions 切换到 OpenAI 原生能力，可以使用 Responses API、Agents SDK、tracing、tool guardrails、input/output guardrails 来实现工具调用审计和安全拦截。  
   但当前 StockM1 依赖 Qwen 与 OpenAI SDK 兼容接口，不能假设所有 OpenAI 原生功能都可用。因此 MVP 应先把结构化输出、tool guardrail 和 tracing 设计成可替换接口。  
   参考：`https://platform.openai.com/docs/api-reference/responses`、`https://openai.github.io/openai-agents-python/guardrails/`、`https://openai.github.io/openai-agents-js/guides/tracing`

5. PydanticAI / Pydantic 输出模型  
   适合 MVP 采用。它的价值不是“更聪明的 Agent”，而是让场景解析、假设、冲击因子、报告结果都有强类型边界。即使不引入 PydanticAI，也应使用 Pydantic/dataclass + JSON Schema 作为模块契约。  
   参考：`https://pydantic.dev/docs/ai/core-concepts/agent/`、`https://pydantic.dev/docs/ai/core-concepts/output/`

#### 2.3.2 金融 Agent 与交易研究框架

1. TradingAgents  
   TradingAgents 提供了一个有参考价值的金融多 Agent 组织结构：基本面、情绪、技术分析、Bull/Bear 研究员、风险管理团队、交易员、基金经理审批。StockM1 可以借鉴其“分析团队 -> 辩论/审查 -> 风险团队 -> 最终审批”的角色设计。  
   但 TradingAgents 的目标是交易决策框架，StockM1 情景推演的目标是压力测试和风险沟通，两者不能简单照搬。尤其不能把 TradingAgents 的收益实验当成 StockM1 的商业或投资收益证明。  
   参考：`https://tradingagents-ai.github.io/`、`https://github.com/TauricResearch/TradingAgents`

2. FinRobot / FinGPT  
   FinRobot 和 FinGPT 说明金融垂直 Agent/LLM 工具链正在形成，包括金融任务分解、模型选择、数据与工具层、面向专业和非专业用户的金融分析接口。StockM1 可以借鉴其分层架构，但不建议直接把金融 LLM 微调作为路线 F 的前置条件。  
   对路线 F 来说，优先级更高的是可审计场景、历史数据校验、组合风险计算和回测，而不是训练专用大模型。  
   参考：`https://papers.ssrn.com/sol3/papers.cfm?abstract_id=4841493`、`https://fingpt.io/`

3. TradeTrap 一类鲁棒性评测  
   最新研究开始关注 LLM 交易 Agent 在扰动、错误信息、组合/账本处理和执行环节中的脆弱性。StockM1 不应只测试“输出是否好看”，还要测试“错误新闻、缺失数据、异常价格、工具返回矛盾时是否会产生极端仓位或错误结论”。  
   参考：`https://huggingface.co/papers/2512.02261`

#### 2.3.3 RAG、Graph RAG 与知识图谱

1. GraphRAG / LightRAG  
   情景推演涉及产业链、政策、行业、上下游、市场叙事等多跳关系，普通向量 RAG 容易只找相似文本，不能稳定表达“事件 -> 因子 -> 行业 -> 个股 -> 组合”的关系链。GraphRAG 与 LightRAG 的启发是：用图结构表达实体关系，用向量检索召回文本证据。  
   MVP 不建议上完整图数据库；V1 可以先用 SQLite 表模拟轻量实体关系；V2 再考虑 Neo4j、LlamaIndex PropertyGraphIndex 或 LightRAG。
   参考：`https://www.microsoft.com/en-us/research/blog/graphrag-improving-global-search-via-dynamic-community-selection/`、`https://huggingface.co/papers/2410.05779`、`https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/`

2. 金融事件因果抽取  
   2025 年已有 LLM-enhanced financial event causality mining 研究，方向上适合路线 F：从金融文本中抽取多因多果关系，形成事件传导链。  
   但这类能力在工程上容易引入误抽取和幻觉关系，因此应先作为离线知识构建工具，而不是实时生产结论来源。所有抽取出的因果边都应带来源、置信度和人工/回测校验状态。  
   参考：`https://link.springer.com/article/10.1007/s44443-025-00330-w`

#### 2.3.4 压力测试与反事实场景生成

1. LLM-generated counterfactual stress scenarios  
   2025 年的相关预印本提出了一个与 StockM1 方向高度一致的架构：结构化提示词 + 可选 RAG + 机器可读宏观场景 + factor-based mapping + VaR/Expected Shortfall + 可复现审计。这个方向支持本文档的核心判断：LLM 适合生成场景和叙事，组合损失要通过因子映射和风险模型计算。  
   但该研究是预印本，不能当作行业定论；StockM1 可以借鉴其“hash artifacts、snapshotting、deterministic mode、scenario diagnostics”的审计思想。  
   参考：`https://ideas.repec.org/p/arx/papers/2512.07867.html`

2. 因果压力测试  
   传统压力测试常依赖相关性，而因果压力测试强调事件顺序和因果网络。StockM1 的“多路径推演”应明确区分相关性、因果假设和纯叙事推断。  
   可落地方式：MVP 用人工模板表达因果链；V1 用历史事件窗口校验方向；V2 再考虑 Suppes-Bayes Causal Networks、Bayesian Networks、结构因果模型或时间序列因果发现。  
   参考：`https://www.sciencedirect.com/science/article/pii/S1877750317311377`

#### 2.3.5 评测、观测与防幻觉

1. DeepEval / RAGAS / Agent trajectory evals  
   情景推演必须有 LLM 评测，不只是传统单元测试。建议建立三类评测：  
   - Faithfulness：报告中的事实是否被证据支持。  
   - Tool trajectory：场景解析、历史类比、因子计算、校验工具是否按预期顺序调用。  
   - Scenario regression：同一黄金场景在不同模型、不同 prompt 下是否保持结构稳定。  
   参考：`https://deepeval.com/docs/metrics-faithfulness`、`https://docs.langchain.com/langsmith/trajectory-evals`

2. OpenTelemetry / AI tracing  
   对金融系统，日志不能只记录最终回答。必须记录每次 LLM 调用、工具调用、输入输出 hash、数据快照 ID、prompt 版本、模型版本、校验结果。OpenTelemetry 生态正在形成 GenAI/Agent observability 规范，可作为未来日志和追踪方案参考。  
   参考：`https://opentelemetry.io/blog/2025/ai-agent-observability/`

### 2.4 技术选型结论

推荐分阶段采用：

| 阶段 | 推荐技术 | 不推荐的做法 |
|---|---|---|
| MVP | Python pipeline + Pydantic/dataclass + JSON Schema + 本地 SQLite + 简化因子模型 + 手工场景模板 | 一开始引入复杂多 Agent 框架、图数据库、自动交易执行 |
| V1 | LangGraph 状态机 + checkpoint + human-in-the-loop + Agent trajectory evals + DeepEval/RAGAS | 让 Agent 自由聊天决定流程；让 LLM 直接输出收益数字 |
| V2 | GraphRAG/LightRAG/Property Graph + 事件因果抽取 + 反向压力测试 + 外部 MCP 数据源 | 无来源知识图谱、不可回测因果链、无法复现的数据抓取 |
| 企业版 | OpenTelemetry tracing + 审计日志 + 权限控制 + 报告版本化 + 模型/数据快照 | 没有审计链路的“黑盒 AI 投顾” |

最终判断：路线 F 可以使用前沿 Agent 和 Graph RAG 技术，但必须采用“确定性计算骨架 + LLM 辅助推理 + 强结构化输出 + 独立校验”的架构。Agent 框架是编排工具，不是金融可信度来源；可信度必须来自数据、模型、审计和回测。

## 三、对原路线 F 的修正判断

原方案中正确的部分：

1. “如果……会怎样”确实是 LLM 相比传统量化界面的交互优势。
2. 多路径推演比单一路径结论更符合金融市场。
3. 历史类比、二阶效应、政策对冲、持仓影响评估是正确的产品方向。
4. 与跨天记忆系统结合是关键壁垒。

原方案中需要修正的部分：

1. 不能把 LLM 的自然语言判断直接当作概率和涨跌幅来源。
2. “目前没有产品做到结构化情景推演”这个判断过强。机构级产品已有压力测试和 what-if，只是未必具备自然语言、多 Agent、A 股垂直和个人化记忆。
3. 只列影响路径不够，必须有场景规范化、风险因子映射、数据证据、数值估计、校验、报告、审计、回测闭环。
4. 对 A 股需要加入制度细节：涨跌停、T+1、行业政策敏感性、北向资金、融资融券、停牌、指数成分变化、主题炒作和散户情绪。

## 四、产品定位

### 4.1 产品名称

StockM1 Scenario Lab：A 股情景推演与组合压力测试引擎。

### 4.2 一句话定位

把用户的自然语言假设转化为可审计的风险因子冲击、多路径市场传导、持仓影响、调仓/对冲候选方案和可回测报告。

### 4.3 核心用户

1. 个人投资者  
   关心“我持有的股票在某政策、宏观、行业事件下会怎样”。

2. 投顾/私募研究员  
   关心“如何对客户组合做压力测试、形成解释材料、比较调仓方案”。

3. 金融科技教学/研究用户  
   关心“如何实验性比较 LLM 推理和传统风险模型”。

### 4.4 不做什么

1. 不输出确定性收益预测。
2. 不直接给“必须买入/卖出”的投资建议。
3. 不承诺替代持牌投顾。
4. 不把新闻热度或 LLM 叙事当作单独交易信号。

## 五、产品功能总览

### 5.1 MVP 功能

1. 自然语言场景输入  
   示例：“如果央行降息 25bp，同时人民币贬值 2%，我当前持仓会怎样？”

2. 场景解析器  
   输出结构化 `ScenarioSpec`：事件类型、冲击对象、方向、幅度、时间范围、置信度、缺失项。

3. 历史类比检索  
   在本地行情中寻找相似历史窗口：降息、汇率、关税、疫情、政策、行业监管等。

4. 因子冲击映射  
   把自然语言事件映射到市场因子：大盘 beta、行业指数、利率代理、汇率代理、商品代理、风险偏好、流动性。

5. 持仓影响计算  
   对每个持仓估算冲击收益区间、贡献、风险等级和主要传导路径。

6. 多路径结果  
   基准路径、乐观路径、悲观路径、反向风险路径。

7. 报告输出  
   结构化 JSON + Markdown 报告 + Streamlit 可视化。

8. 防幻觉审计  
   每个数值结论必须标记来源：历史样本、因子模型、用户假设、LLM 推理。

### 5.2 V1 功能

1. 场景库  
   内置：降息、加息、汇率贬值、关税升级、地产政策放松、白酒限制、半导体出口管制、新能源补贴退坡、油价冲击、海外市场暴跌。

2. 组合 what-if  
   支持“如果减仓 A、加仓 B、现金提高到 40%，情景结果如何变化”。

3. 反向压力测试  
   输入损失阈值：“什么样的情景会让我的组合亏损超过 10%？”

4. 多 Agent 评审  
   Bull Agent、Bear Agent、Risk Agent、Policy Agent、Quant Agent 分别审查同一情景。

5. 记忆系统接入  
   保存历史情景、预测区间、实际结果、用户操作和复盘教训。

### 5.3 V2 功能

1. Graph RAG 金融知识图谱  
   产业链、供应链、股东关系、行业政策、主题映射。

2. 事件驱动监控  
   当真实新闻接近某个场景模板时自动触发提醒。

3. 多资产扩展  
   指数、ETF、期货、债券、黄金、外汇代理因子。

4. 企业版报告  
   客户级组合批量压力测试、审计日志、权限控制、合规免责声明。

## 九、核心算法设计

### 9.1 场景解析

输入：

```text
如果中美贸易战升级，对半导体板块加征 25% 关税，我持仓会怎样？
```

输出：

```json
{
  "event_type": "policy",
  "event_name": "中美贸易摩擦升级：半导体关税上调",
  "region": "GLOBAL",
  "horizon": "3m",
  "affected_entities": ["半导体", "电子", "出口链", "国产替代"],
  "shocks": [
    {"factor": "semiconductor_export_tariff", "direction": "up", "magnitude": 25, "unit": "pct"},
    {"factor": "risk_appetite", "direction": "down", "magnitude": 1, "unit": "score"}
  ],
  "missing_information": ["关税适用范围", "执行日期", "豁免清单"]
}
```

解析器要求：

1. 必须输出符合 JSON Schema 的结构化数据。
2. 不确定字段不能编造，放入 `missing_information`。
3. 用户未给时间范围时，默认输出 `1w/1m/3m` 三个 horizon。
4. 每个冲击必须有 `source`。

### 9.2 历史类比检索

候选方法：

1. 关键词模板匹配  
   例如：贸易战、降息、加息、地产政策、疫情、出口管制。

2. 事件窗口库  
   手工维护典型事件日期窗口：
   - 2018-2019 中美贸易摩擦
   - 2020 疫情冲击
   - 2021 教培/互联网监管
   - 2022 地产信用压力
   - 2023-2024 AI 算力与半导体主题

3. 市场状态相似度  
   使用事件前 N 日的指数收益、波动率、成交额、行业相对强弱、技术指标，计算相似历史窗口。

4. 记忆检索  
   从跨天记忆中的 `event_memory`、`trade_lessons`、`daily_digest` 检索类似事件。

输出：

```python
HistoricalAnalog(
    event_name="2018 中美贸易摩擦升级",
    window=("2018-06-15", "2018-09-15"),
    similarity=0.73,
    market_return=-0.12,
    industry_returns={"半导体": -0.18, "黄金": 0.06},
    notes="初期风险偏好下行，随后国产替代主题反弹"
)
```

### 9.3 因子暴露估计

当前 StockM1 主要有股票和指数日线数据，MVP 可先实现简化因子模型：

```text
stock_return = alpha
             + beta_market * index_return
             + beta_industry * industry_proxy_return
             + beta_momentum * momentum_factor
             + beta_volatility * volatility_factor
             + residual
```

MVP 因子：

1. `market_beta`：相对沪深300或上证指数的 beta。
2. `industry_proxy_beta`：用股票池内同类股票或用户配置行业代理。
3. `momentum_beta`：20 日/60 日动量。
4. `volatility_sensitivity`：历史波动率上升时的表现。
5. `liquidity_sensitivity`：成交额萎缩时的表现。

后续扩展：

1. 接入申万行业指数。
2. 接入利率、汇率、商品、北向资金。
3. 接入 Barra/CNE5 风格因子替代版：规模、价值、动量、波动、流动性、成长、杠杆。

### 9.4 冲击传播

冲击传播分三层。

第一层：直接因子冲击  
例如降息 25bp -> 利率因子下行 -> 金融、地产、成长股估值敏感。

第二层：行业与主题传导  
例如关税升级 -> 出口链承压 -> 国产替代主题升温 -> 半导体设备、材料可能相对受益。

第三层：市场行为反馈  
例如风险偏好下降 -> 高估值板块估值压缩 -> 避险资产或高股息风格相对占优。

每条路径必须输出：

1. 传导步骤。
2. 影响方向。
3. 时间滞后。
4. 证据来源。
5. 反向条件。

### 9.5 多路径推演

标准模式建议生成以下路径，其中 Base/Bull/Bear 为必需路径，Reflexive 为证据充足时的可选路径：

1. Base Path  
   最符合历史类比和当前市场状态的路径。

2. Bull Path  
   政策对冲、预期修复、流动性改善或主题强化的路径。

3. Bear Path  
   事件扩大、风险偏好坍塌、估值杀跌的路径。

4. Reflexive Path  
   市场先交易预期，随后出现反转或二阶效应的路径。该路径不是所有情景都必然出现；MVP 可以先作为可选路径，当证据不足时只输出 Base/Bull/Bear。

输出不是单点收益率，而是区间：

```json
{
  "portfolio_impact": {
    "base": [-0.045, -0.018],
    "bull": [0.005, 0.032],
    "bear": [-0.115, -0.062],
    "reflexive": [-0.070, 0.018]
  }
}
```

### 9.6 反向压力测试

输入：

```text
什么情景会让我的组合在 1 个月内亏损超过 8%？
```

流程：

1. 读取当前持仓和权重。
2. 估计每个持仓的因子暴露。
3. 枚举风险因子冲击组合。
4. 找到满足组合损失阈值的最小冲击组合。
5. 用 LLM 解释这些冲击组合在现实中可能对应哪些事件。

输出示例：

```text
最脆弱组合：
- 沪深300 下跌 8%
- 半导体行业相对大盘再下跌 10%
- 成交额下降 25%
- 人民币贬值引发外资流出

现实叙事：
- 海外制裁升级 + 国内流动性偏紧 + 高估值科技股杀估值
```

### 9.7 What-If 调仓比较

支持用户输入：

```text
如果把中芯国际仓位从 15% 降到 8%，把现金提高到 30%，结果会怎样？
```

比较：

1. 当前组合。
2. 用户假设组合。
3. 系统生成的风险控制候选组合。该组合只能作为压力测试比较对象，必须由用户确认，不能包装成确定性投资建议。

指标：

1. 场景损失区间。
2. 上行机会损失。
3. 最大单一风险来源。
4. 行业集中度。
5. 流动性压力。

### 10.2 Agent 分工

1. Scenario Parser Agent  
   只负责解析场景，不输出投资建议。

2. Evidence Agent  
   负责找历史类比、记忆、事件窗口和数据证据。

3. Quant Agent  
   负责因子暴露、冲击计算、组合贡献。

4. Bull Agent  
   寻找正向路径和政策对冲。

5. Bear/Risk Agent  
   寻找下行路径、脆弱点和反向压力情景。

6. Critic Agent  
   检查是否有幻觉、未来数据、缺失来源、概率乱填。

7. Report Agent  
   只基于前面结构化结果生成报告。

### 10.3 编排方式

MVP 不必引入 LangGraph，先用普通 Python pipeline 保持简单。  
V1 当 Agent 节点变多、需要状态持久化和人工确认时，再引入 LangGraph。

推荐状态机：

```text
CREATED
  → PARSED
  → EVIDENCE_READY
  → QUANT_READY
  → AGENT_REVIEW_READY
  → VALIDATED
  → REPORTED
  → SAVED_TO_MEMORY
```

## 十二、报告输出规范

报告必须包含以下固定结构：

1. 执行摘要  
   用 5-8 行说明结论，不得使用确定性语言。

2. 场景定义  
   明确用户输入、系统解析、冲击因子、时间范围、缺失信息。

3. 核心传导路径  
   每条路径列出因果链、方向、时间滞后、证据。

4. 组合影响  
   输出当前组合总影响区间、分持仓贡献、行业集中度。

5. 多路径结果  
   Base/Bull/Bear/Reflexive 四条路径。

6. 可选操作  
   只输出“候选动作”，如减仓、提高现金、替换标的、设置观察条件，不输出强制建议。

7. 风险与不确定性  
   明确哪些结论依赖假设，哪些缺数据。

8. 审计表  
   每个关键数字对应来源。

## 十三、开发模式选择

推荐 PDD + TDD。

### 13.1 为什么不是纯 TDD

情景推演产品含有大量开放式金融语义、用户输入、报告表达和合规边界。纯 TDD 容易先写出局部函数，却没有先锁定用户工作流和输出责任。

### 13.2 为什么不是纯 PDD

核心计算模块必须可测，否则系统会退化成漂亮但不可验证的 LLM 文案。因子暴露、历史窗口检索、组合冲击计算、反向压力测试都必须 TDD。

### 13.3 推荐流程

1. PDD 阶段  
   先写产品样例、报告样例、JSON Schema、页面草图、合规免责声明。

2. Contract Test 阶段  
   为 `ScenarioSpec`、`ScenarioReport`、工具输出写契约测试。

3. TDD 阶段  
   为解析后处理、历史类比、因子暴露、冲击传播、组合贡献写单元测试。

4. Golden Scenario 阶段  
   固定 10 个典型场景作为黄金样例，每次改动比较输出结构和关键指标。

5. Backtest 阶段  
   用历史日期做 walk-forward 验证，不允许使用未来数据。

## 十五、测试策略

### 15.1 单元测试

1. 场景解析后处理  
   测试缺失字段、单位转换、bp/pct 区分。

2. 历史类比  
   测试相似度排序、时间窗口不越界、未来数据禁用。

3. 因子暴露  
   测试 beta 计算、缺失数据处理、极端值截尾。

4. 组合冲击  
   测试权重贡献、现金仓位、空持仓、停牌价格缺失。

5. 报告审计  
   测试每个 impact 数字都能关联 evidence。

### 15.2 集成测试

黄金场景：

1. 降息 25bp。
2. 加息 50bp。
3. 人民币贬值 3%。
4. 中美关税升级。
5. 半导体出口限制。
6. 地产政策放松。
7. 油价上涨 20%。
8. 海外市场单日暴跌 5%。
9. 白酒行业监管。
10. 新能源补贴退坡。

### 15.3 回测测试

Walk-forward 原则：

1. 选择历史某日作为 `as_of_date`。
2. 系统只能读取该日及以前数据。
3. 生成未来 1w/1m/3m 区间。
4. 对比真实后续收益是否落入区间。
5. 记录命中率、方向准确率、区间宽度、最大误差。

### 15.4 LLM 测试

1. Schema 合规率。
2. 缺失信息识别率。
3. 幻觉数字检测率。
4. 对同一场景多次运行稳定性。
5. Critic 对风险措辞的拦截率。

## 十六、合规与风险控制

1. 报告开头必须声明：结果是情景分析和压力测试，不是收益承诺。
2. 所有操作建议必须表述为“候选动作/风险管理选项”。
3. 禁止出现“必涨、必跌、稳赚、确定性机会”等措辞。
4. LLM 不得独立生成具体价格目标，除非来自模型计算或用户假设。
5. 对数据缺失、样本少、历史不可比的情况必须降置信度。
6. 企业版必须保留审计日志：输入、模型版本、数据版本、输出、人工确认。

## 十八、MVP 伪代码

```python
def run_scenario(user_query: str, as_of_date: str, portfolio: dict) -> ScenarioReport:
    parsed = parser.parse(user_query, as_of_date)
    spec = normalizer.normalize(parsed)

    evidence = EvidenceBundle()
    evidence.analogs = analog_retriever.find(spec, as_of_date, top_k=5)
    evidence.exposures = factor_model.estimate(portfolio.symbols, as_of_date)
    evidence.portfolio = portfolio

    paths = path_builder.build(spec, evidence)
    impacts = simulator.simulate(spec, paths, evidence.exposures, portfolio)

    draft = report_agent.compose(spec, paths, impacts, evidence)
    validation = validator.validate(draft)

    if not validation.ok:
        draft = report_agent.repair(draft, validation.issues)

    report = reporter.to_report(draft)
    repository.save(report)
    return report
```

## 十九、关键产品细节

### 19.1 概率如何处理

MVP 不输出精确概率，只输出：

- 高：有多个历史类比和当前条件支持。
- 中：有部分历史类比，但当前条件不同。
- 低：主要来自逻辑推演或样本不足。

V1 后可以把概率拆成：

1. `historical_frequency`
2. `model_likelihood`
3. `llm_judgment`
4. `final_confidence`

### 19.2 收益区间如何处理

收益区间来自三部分：

1. 历史相似事件的分位数。
2. 因子暴露乘以假设冲击。
3. 波动率调整后的误差带。

禁止让 LLM 直接拍脑袋输出 “-15%”。

### 19.3 A 股特殊逻辑

必须支持：

1. 涨跌停导致的冲击延迟释放。
2. T+1 导致无法当日卖出。
3. 停牌导致无法成交。
4. 行业政策一刀切带来的相关性上升。
5. 主题交易导致短期非线性反应。
6. 小市值流动性风险。

### 19.4 UI 交互细节

用户输入场景后，系统先展示“场景解析结果”，让用户确认：

```text
我理解你的场景为：
- 事件：央行降息
- 幅度：25bp
- 时间：未来 1 个月
- 影响因子：利率、风险偏好、地产/金融/成长风格
- 缺失信息：是否同时降准、是否有财政政策配合
```

用户确认后再运行深度推演。快速模式可以跳过确认。

## 二十、最终建议

路线 F 应作为 StockM1 的 P1 核心差异化能力推进，但实施优先级应在“跨天记忆、数据层、结构化输出、基础因子模型”之后。

最现实的落地路线是：

1. 先做 MVP：自然语言场景 -> 结构化解析 -> 历史类比 -> 持仓影响 -> 报告。
2. 再做 V1：反向压力测试、调仓比较、多 Agent 审查。
3. 最后做 V2：知识图谱、实时事件触发、企业级批量压力测试。

这不应被设计成“LLM 炫技功能”，而应被设计成可进入投研、投顾、风控和用户教育工作流的产品模块。它的潜在壁垒不在于会说“如果……会怎样”，而在于每次推演都能被数据校验、被记忆复盘、被用户用于真实决策前的风险沟通。
