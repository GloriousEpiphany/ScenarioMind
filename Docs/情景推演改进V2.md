# 情景推演实验室改进 V2.1：金融证据研究、主体图谱沙盘与可审计多 Agent 推演方案

> 本文档整合 `Docs/情景推演改进.md`、现有 `scenario_engine` 代码、TrendRadar 的外部资讯采集思路，以及临时参考项目 `MiroFish` 的群体智能/图谱仿真产品思想。  
> 重要边界：`MiroFish` 只作为方法参照，不作为 StockM1 运行依赖；后续删除 `MiroFish` 文件夹后，StockM1 仍必须完整运行。实现时不得直接复制或 import `MiroFish` 文件夹代码。

---

## 1. 升级结论

现有 V2 已经把情景推演从“本地行情压力测试”推进到“外部证据驱动的研究 Agent”。当前代码中已具备以下基础：

- `scenario_engine/engine.py` 已在 `ScenarioEngine.run()` 中接入 `ResearchOrchestrator`、外部证据转换、知识图谱增强、证据修正、Agent 审查、审计与报告。
- `scenario_engine/research/` 已有 `ResearchPlan`、`ExternalEvidenceDocument`、`ResearchRepository`、`ScenarioEvidenceClassifier`、RSS/页面抓取、正文读取和证据评分。
- `scenario_engine/evidence_adjuster.py` 已明确外部证据只能调整区间宽度、方向倾向和置信度，不能生成收益数字。
- `scenario_engine/knowledge_graph.py` 已有轻量本地图谱，可表达事件、实体、历史窗口和关系边。
- `scenario_engine/event_scheduler.py` 已有事件轮询调度能力。

新的改进目标不是再重复“接入热榜/RSS”，而是把系统推到更高一层：

```text
外部事实证据层
  + 金融主体图谱层
  + 市场参与者画像层
  + 时间推进沙盘层
  + 干预实验层
  + 量化压力测试层
  + 报告与审计层
```

最终产品应定位为：

> StockM1 Scenario Lab 是一个面向 A 股持仓的金融情景推演与组合压力测试实验室。它用可审计数据和确定性模型计算组合影响，用金融主体图谱和多 Agent 沙盘解释市场传导、参与者行为与反向条件，用普通投资者能理解的话输出结论，但不替代持牌投顾，不给确定性买卖指令。

## 2. 对 MiroFish 的方法评估与金融化改造

### 2.1 可借鉴的方法

MiroFish 的核心工作流可概括为：

```text
种子材料上传
-> 本体生成
-> 图谱构建
-> 主体画像生成
-> 仿真配置生成
-> 多平台/多轮模拟
-> 动态记忆更新
-> Report Agent 检索模拟世界并生成报告
-> 用户与模拟世界交互
```

对 StockM1 有价值的不是其社交平台实现，而是这些工程思想：

- 从“种子材料”中抽取实体、关系、立场、事件和时间线。
- 先生成领域本体，再构建知识图谱，避免只有向量相似度而缺少结构。
- 给每类主体生成画像、活跃度、响应延迟、影响力和偏好。
- 分步生成仿真配置，避免一次性让 LLM 输出超长配置导致失败。
- 用轮次和模拟时间推进事件，而不是一次性生成静态报告。
- 记录每个 Agent 的动作、轮次、工具调用和报告生成日志。
- Report Agent 不是凭空写报告，而是反复检索图谱、行动记录和模拟结果。
- 允许用户在模拟过程中注入变量，观察系统如何变化。

### 2.2 不能照搬的部分

金融情景推演必须比通用舆情模拟更严格：

- 不能把“群体涌现结果”当成真实收益率预测。
- 不能把普通社交平台互动规则当作 A 股市场交易机制。
- 不能让 LLM Agent 自由创造价格、成交量、基本面指标或概率。
- 不能把热度、转发、观点数量直接映射为买卖建议。
- 不能依赖临时项目文件夹、外部私有服务或不可复现图谱服务。

因此，MiroFish 只能启发 StockM1 增加一个“金融主体沙盘层”，它服务于解释、反事实、风险识别和报告论证；组合损益仍由现有确定性压力测试、历史类比、因子暴露、约束分析和回测模块负责。

### 2.3 金融化后的新范式

MiroFish 的“社会主体”应改造成“金融市场参与者与约束主体”：

| 通用仿真概念 | 金融化概念 | StockM1 中的用途 |
|---|---|---|
| 人物/组织实体 | 央行、财政部、交易所、上市公司、行业、机构资金、散户、媒体、外资、融资盘 | 构建事件传导主体 |
| 社交关系 | 监管、融资、持股、供应链、客户、行业竞争、政策约束、信息传播 | 构建金融知识图谱 |
| 发帖/评论/转发 | 公告、研报、交易行为、资金流、市场解读、风险披露、媒体报道 | 形成证据与行为轨迹 |
| 活跃时间 | 交易时段、公告时段、政策发布窗口、财报季、海外市场时区 | 时间推进和事件触发 |
| 影响力 | 来源权威性、资金规模、行业地位、指数权重、舆情传播力 | 证据权重与传导强度 |
| 情感立场 | 风险偏好、政策预期、估值偏好、久期偏好、行业拥挤度 | Bull/Bear/Risk 路径权重 |
| 动态注入变量 | 降息、汇率冲击、监管政策、财报暴雷、地缘冲突、流动性变化 | What-if 干预实验 |

## 3. V2.1 总体架构

```text
用户情景 + 当前持仓 + 基准日期
  -> Scenario Parser：结构化情景与缺失项
  -> Research Planner：研究问题、查询词、数据源预算
  -> Evidence Collectors：政策/公告/新闻/RSS/热榜/本地行情/宏观代理
  -> Evidence Repository：去重、评分、正文、热度轨迹、审计
  -> Financial Ontology Builder：生成或加载金融本体
  -> Financial Graph Builder：主体、事件、因子、行业、持仓、证据入图
  -> Participant Profile Builder：市场参与者画像与约束
  -> Simulation Config Generator：时间、事件、主体、干预和观测指标配置
  -> Market Sandbox Runner：多轮金融主体沙盘，不直接生成收益数字
  -> Quant Engine：历史类比、因子暴露、冲击映射、组合压力测试
  -> Evidence Impact Adjuster：只调整置信度、路径权重和区间宽度
  -> Agent Review Council：Bull/Bear/Risk/Policy/Quant/Evidence Critic
  -> Retail Report Composer：普通投资者可读报告
  -> Audit & Replay：证据链、模型版本、数据快照、Agent 轨迹、回测复盘
```

这套架构把系统分成三条互相制衡的链路：

1. **事实链**：外部证据、公告、政策、行情、财报、来源质量、抓取时间。
2. **计算链**：历史窗口、因子暴露、A 股制度约束、组合贡献、区间估计。
3. **解释链**：金融主体图谱、多 Agent 沙盘、正反路径、反向条件、投资者报告。

任何最终结论都必须能说明来自哪条链；收益区间只能来自计算链；解释和风险触发条件可以来自事实链与解释链。

## 4. 现有 V2 能力与下一步差距

### 4.1 已完成或已具备雏形的能力

从当前代码看，以下内容不应再作为“从零新增”的目标，而应作为迭代基础：

- `ResearchOrchestrator.collect()`：已能规划查询、按来源采集、分类、正文读取、入库并输出 `ResearchBundle`。
- `ResearchRepository`：已创建 `scenario_external_sources`、`scenario_external_evidence`、`scenario_external_rank_history`、`scenario_external_crawl_runs`、`scenario_external_source_status`。
- `ExternalEvidenceDocument`：已覆盖来源、URL、发布时间、首次发现、最后发现、出现次数、排名轨迹、正文、实体、标签、相关股票、相关性、来源质量、新鲜度和综合分。
- `EvidenceImpactAdjuster`：已形成“证据不能生成收益，只能修正区间和信心”的正确边界。
- `LocalKnowledgeGraph`：已可从模板和文本中建立轻量图谱，并与情景规格做增强。
- `EventPollingScheduler`：已能定时轮询事件源并触发告警或自动运行。
- `ScenarioFullAgentWorkflow`、`ScenarioAgentReview`：已有多 Agent 审查框架雏形。

### 4.2 需要补足的关键差距

V2.1 的主要缺口是：

- 图谱还偏“模板/文本关系”，缺少金融本体与持仓相关实体类型。
- Agent 仍偏报告审查，缺少可复跑的“金融主体沙盘”状态、轮次和动作日志。
- Research Planner 已能规划查询，但还不能生成“仿真配置”：哪些主体被激活、什么时间触发、观察哪些指标、什么条件改变路径权重。
- 外部证据已能入库，但还没有系统性进入“主体画像”和“事件时间线”。
- 报告已有证据链，但还缺少“模拟后世界观”：哪些主体可能先反应、谁的行为可能放大或缓冲冲击、什么反事实注入会改变结论。

## 5. 金融本体与图谱设计

### 5.1 金融本体原则

参考 MiroFish 的“先本体、再图谱”思想，但金融本体必须稳定、可审计、可扩展。MVP 不建议每次完全让 LLM 自由生成本体，应采用“内置金融本体 + LLM 补充候选 + 人工/规则校验”的方式。

核心实体类型：

- `PolicyAuthority`：央行、财政部、证监会、交易所、地方政府。
- `ListedCompany`：上市公司及其公告、财务、行业属性。
- `Industry`：申万/中信行业、主题链、上游/下游。
- `MacroFactor`：利率、信用、汇率、通胀、PMI、财政、流动性。
- `MarketIndex`：沪深300、上证指数、中证银行、创业板等。
- `PortfolioPosition`：用户持仓、权重、成本、流动性约束。
- `InvestorGroup`：公募、私募、外资、散户、融资盘、保险、银行理财。
- `MediaSource`：官方媒体、财经媒体、社区舆情、研报源。
- `Event`：政策事件、公司事件、行业事件、海外冲击、市场异常。
- `EvidenceDocument`：政策、公告、新闻、财报、热榜、研究摘录。

核心关系类型：

- `REGULATES`：监管/政策约束。
- `AFFECTS_FACTOR`：事件影响风险因子。
- `EXPOSED_TO`：公司/组合暴露于某因子。
- `BELONGS_TO_INDUSTRY`：公司所属行业。
- `SUPPLY_CHAIN_LINK`：上下游关系。
- `HOLDS_OR_TRADES`：资金主体持有或交易方向。
- `REPORTS_ON`：媒体报道事件。
- `SUPPORTS_PATH`：证据支持某条传导路径。
- `CONTRADICTS_PATH`：证据反驳某条传导路径。
- `TRIGGERS_CONDITION`：证据或指标触发反向条件。

### 5.2 图谱数据结构

建议在现有 `KnowledgeNode`、`KnowledgeEdge` 基础上扩展字段，而不是引入重型图数据库：

```python
@dataclass
class FinancialGraphNode:
    node_id: str
    node_type: str
    name: str
    description: str
    source: str
    confidence: float
    as_of_date: str
    attributes: dict
    evidence_ids: list[str]
    audit: dict
```

```python
@dataclass
class FinancialGraphEdge:
    edge_id: str
    source_node_id: str
    target_node_id: str
    relation_type: str
    direction: str
    confidence: float
    lag_days: tuple[int, int] | None
    evidence_ids: list[str]
    validation_status: str  # template / evidence_supported / backtested / disputed
    audit: dict
```

### 5.3 图谱构建来源

图谱不能只靠 LLM 抽取，应按来源分层：

1. **确定性来源**：用户持仓、股票代码、行业分类、本地行情、情景模板。
2. **权威来源**：央行/交易所/公司公告/财报/监管文件。
3. **资讯来源**：财经媒体、RSS、热榜、海外新闻。
4. **LLM 抽取来源**：从长文中抽取候选实体和候选关系，必须带 `evidence_id` 和置信度。
5. **回测来源**：历史事件后验证过的传导边，提高 `validation_status`。

## 6. 市场参与者画像层

### 6.1 为什么需要画像

传统压力测试能回答“组合可能跌多少/涨多少”，但投资者还想知道：

- 谁会先反应？
- 哪类资金会放大波动？
- 政策发布后市场为什么可能先涨后跌？
- 平安银行这类持仓为什么既可能受益于宽信用，又可能承压于净息差？
- 什么证据会让结论从 Bull 转向 Bear？

这些问题适合由“金融主体沙盘”解释，但不能由它生成收益数字。

### 6.2 参与者画像字段

```python
@dataclass
class MarketParticipantProfile:
    participant_id: str
    participant_type: str  # policy_authority / listed_company / investor_group / media / analyst / retail
    name: str
    mandate: str
    information_sources: list[str]
    decision_rules: list[str]
    risk_preferences: dict
    response_delay: dict
    influence_weight: float
    constraints: list[str]
    likely_actions: list[str]
    evidence_ids: list[str]
    confidence: float
```

金融画像示例：

- `PolicyAuthority: PBOC`：目标包括稳增长、防风险、汇率稳定；动作包括 OMO、MLF、LPR 引导、降准、窗口指导。
- `InvestorGroup: 公募基金`：关注政策预期、估值、行业拥挤度、赎回压力；可能在确认宽信用后提高权益仓位。
- `InvestorGroup: 融资盘`：对下跌和波动更敏感；可能放大短期下行。
- `MediaSource: 财经媒体`：放大政策解读和市场预期，但质量分取决于来源。
- `ListedCompany: 平安银行`：同时暴露于银行净息差、地产链资产质量、宽信用、估值修复。

### 6.3 画像生成规则

画像生成应分三步：

1. **模板初始化**：根据实体类型加载基础规则，确保没有 LLM 也能运行。
2. **证据补充**：从公告、财报、新闻、历史事件中补充当前画像。
3. **LLM 摘要**：只生成可读描述和候选行为，不生成数值收益或交易指令。

## 7. 金融沙盘仿真配置生成

### 7.1 设计目标

参考 MiroFish 的分步配置生成方式，StockM1 应新增 `FinancialSimulationConfigGenerator`。它不直接运行社交媒体模拟，而是生成金融情景沙盘所需的可审计配置。

配置生成必须分步：

1. 时间配置。
2. 初始事件与定时事件。
3. 参与者配置。
4. 市场机制配置。
5. 观察指标配置。
6. 干预实验配置。

这样能避免一次性 LLM 输出过长，也便于每一步校验。

### 7.2 配置数据结构

```python
@dataclass
class FinancialTimeConfig:
    total_simulation_days: int
    step_minutes: int
    trading_sessions: list[dict]
    announcement_windows: list[dict]
    overseas_sessions: list[dict]
    event_lag_rules: dict
```

```python
@dataclass
class FinancialEventConfig:
    initial_events: list[dict]
    scheduled_events: list[dict]
    possible_followups: list[dict]
    trigger_conditions: list[dict]
    narrative_hypotheses: list[dict]
```

```python
@dataclass
class FinancialSandboxConfig:
    scenario_id: str
    as_of_date: str
    time_config: FinancialTimeConfig
    participant_profiles: list[MarketParticipantProfile]
    event_config: FinancialEventConfig
    market_mechanism: dict
    observation_metrics: list[str]
    intervention_points: list[dict]
    audit: dict
```

### 7.3 A 股时间机制

通用作息时间应替换为金融时间：

- 盘前：公告、政策、海外市场影响、集合竞价预期。
- 上午盘：开盘冲击、资金抢跑、指数权重反应。
- 午间：媒体解读、券商观点、公告补充。
- 下午盘：机构再平衡、融资盘压力、尾盘资金。
- 盘后：龙虎榜、公告、研报、监管问询、海外期货/汇率。
- 周末/节假日：政策发布高发但无法交易，次交易日集中反映。

### 7.4 仿真输出边界

沙盘输出只允许包括：

- 主体可能动作。
- 信息传播路径。
- 风险偏好方向。
- Bull/Bear/Reflexive 路径的证据支持度。
- 哪些指标需要观察。
- 哪些反向条件被触发。

沙盘输出不允许包括：

- 个股确定涨跌幅。
- 组合收益区间。
- “必须买入/卖出”。
- 无来源概率。
- 伪造公告、财报或市场数据。

## 8. 多轮金融沙盘 Runner

### 8.1 Runner 目标

新增 `FinancialSandboxRunner`，用于在一个情景中推进多轮状态。它不是撮合交易引擎，也不是价格生成器，而是“事件解释与参与者行为模拟器”。

每轮输入：

- 当前时间步。
- 已发生事件。
- 最新证据。
- 参与者画像。
- 当前路径状态。
- 量化引擎上一轮输出摘要。

每轮输出：

- 主体动作记录。
- 信息扩散记录。
- 风险偏好变化。
- 路径支持/反驳变化。
- 需要量化引擎重新计算的触发项。
- 审计日志。

### 8.2 动作记录结构

```python
@dataclass
class FinancialAgentAction:
    round_num: int
    simulated_time: str
    participant_id: str
    participant_name: str
    action_type: str  # publish_policy / file_announcement / buy_pressure / sell_pressure / media_interpretation / risk_warning
    action_summary: str
    evidence_ids: list[str]
    affected_paths: list[str]
    confidence: float
    requires_quant_recalc: bool
    audit: dict
```

### 8.3 状态结构

```python
@dataclass
class FinancialSandboxState:
    sandbox_id: str
    scenario_id: str
    status: str
    current_round: int
    total_rounds: int
    path_scores: dict
    participant_states: dict
    triggered_conditions: list[dict]
    actions: list[FinancialAgentAction]
    latest_quant_snapshot_id: str | None
    audit: dict
```

### 8.4 与量化引擎的关系

沙盘和量化引擎采用“弱耦合闭环”：

```text
沙盘识别路径/条件变化
  -> 生成 quant_recalc_request
  -> ScenarioSimulator / EvidenceImpactAdjuster 重新计算或修正
  -> 新的量化摘要进入下一轮沙盘
```

注意：沙盘只能提出“需要重算哪个因子/路径”，不能直接改组合收益。

## 9. Agent 角色升级

现有 Bull/Bear/Risk/Evidence Critic 可以保留，但 V2.1 应将角色分成两类。

### 9.1 研究与计算 Agent

- `ResearchPlannerAgent`：已有雏形，继续负责研究问题、查询词、来源预算。
- `PolicyCollectorAgent`：政策、央行、财政、交易所。
- `AnnouncementCollectorAgent`：公司公告、财报、问询。
- `MarketDataAgent`：本地行情、指数、行业、代理资产。
- `EvidenceNormalizerAgent`：清洗标题、URL、时间、实体、标签和质量分。
- `QuantAgent`：只解释确定性量化结果，不生成数字。

### 9.2 沙盘与审查 Agent

- `OntologyAgent`：基于内置金融本体和证据补充实体/关系候选。
- `ProfileAgent`：生成市场参与者画像。
- `EventTimelineAgent`：把证据整理为事件时间线。
- `SandboxConfigAgent`：分步生成仿真配置。
- `BullAgent`：寻找正向传导路径。
- `BearAgent`：寻找下行传导路径。
- `RiskAgent`：寻找组合脆弱点、拥挤交易、流动性风险。
- `PolicyAgent`：检查政策口径、监管边界和政策组合。
- `EvidenceCriticAgent`：检查证据是否过期、来源是否弱、是否有反证。
- `RetailReportAgent`：把复杂结论翻译为普通投资者能读懂的话。

每个 Agent 输出必须包含：

- `agent_name`
- `input_snapshot_id`
- `tool_calls`
- `evidence_ids`
- `claims`
- `uncertainty`
- `audit`

## 12. 降息 25bp + 平安银行重仓验收样例

### 12.1 研究问题

用户输入：

```text
如果央行降息 25bp，我重仓平安银行，会怎样？
```

系统必须自动拆成：

- 降息是否已发生，还是用户假设？
- 是 OMO、MLF、LPR 还是存款利率同步变化？
- 市场是否已提前定价？
- 对银行净息差是压力还是被存款利率下调对冲？
- 宽信用是否改善地产链和资产质量预期？
- 平安银行自身基本面、地产敞口、零售风险是否会放大下行？
- 银行板块历史降息窗口表现如何？
- 当前估值、趋势、波动、舆情是否支持修复路径？

### 12.2 图谱节点

应至少形成：

- `PolicyAuthority: 中国人民银行`
- `MacroFactor: LPR/MLF/OMO/存款利率`
- `MacroFactor: 社融/信用扩张`
- `Industry: 银行`
- `Industry: 房地产链`
- `ListedCompany: 平安银行`
- `InvestorGroup: 机构资金`
- `InvestorGroup: 散户/融资盘`
- `MarketIndex: 中证银行/沪深300`
- `EvidenceDocument: 央行公告/财经报道/公司公告/历史窗口`

### 12.3 正反路径

Bull Path：

```text
降息 + 存款利率同步下调
-> 银行负债成本下降
-> 净息差压力被部分对冲
-> 宽信用和地产政策改善资产质量预期
-> 银行估值修复
-> 平安银行重仓组合受益
```

Bear Path：

```text
被动降息反映经济压力
-> 贷款收益率下行快于负债成本
-> 银行净息差继续承压
-> 地产/零售资产质量担忧升温
-> 银行板块估值被压制
-> 平安银行集中仓位放大组合波动
```

Reflexive Path：

```text
市场先交易宽松预期上涨
-> 随后财报/社融/地产销售验证不足
-> 资金兑现或风格切换
-> 银行股冲高回落
```

### 12.4 报告口径

报告必须类似这样表达：

```text
降息 25bp 对你的组合不是简单利好。平安银行权重较高时，核心矛盾是“流动性改善带来的估值修复”和“贷款利率下行带来的净息差压力”谁更强。如果降息同时伴随存款利率下调、社融改善和地产风险缓和，银行股修复路径更容易成立；如果降息被市场理解为经济压力加大，且平安银行资产质量担忧升温，你的组合会因为银行集中度较高而更脆弱。
```

不得输出：

- “建议立刻买入/卖出平安银行”。
- “平安银行必涨/必跌”。
- 由 LLM 直接编造的收益率。

## 13. 报告结构升级

新版报告建议固定结构：

```text
1. 一句话结论
2. 行动判断：需要调仓 / 暂不行动 / 等待确认 / 证据不足
3. 对你的组合意味着什么
4. 最大风险持仓与风险来源
5. 金融主体沙盘摘要：谁先反应、谁放大、谁缓冲
6. Bull / Bear / Reflexive 三条路径
7. 关键观察信号
8. 调仓/对冲候选方案，仅作为压力测试比较
9. 证据链：政策、公告、行情、新闻、历史窗口
10. Agent 审查记录
11. 数据边界、模型边界与合规免责声明
12. 可复盘项：未来 N 日验证哪些条件
```

报告语气要求：

- 面向普通投资者，少用空泛术语。
- 每个强判断都带 `evidence_id`。
- 数值区间必须标明来自历史类比、因子模型还是组合压力测试。
- 当证据不足时明确说“不足以判断”。
- 候选动作必须是条件化表达，例如“如果 X 被验证，再比较 Y 方案”，而不是直接指令。

- `financial_compliance`：是否出现确定性荐股、收益承诺或无证据买卖指令。

## 16. MVP 建议

不要一开始实现完整群体智能平台。最小闭环建议是：

```text
1. 保留现有 ResearchOrchestrator 和 EvidenceImpactAdjuster。
2. 新增内置金融本体，不依赖外部图数据库。
3. 把外部证据、持仓、行业、因子写入本地图谱。
4. 为 6 类主体生成规则化画像：央行/监管、上市公司、机构资金、散户/融资盘、媒体、用户持仓。
5. 为降息样例生成 3-5 轮沙盘动作。
6. 沙盘只输出路径支持度和反向条件。
7. 最终报告展示“证据链 + 量化区间 + 主体沙盘解释”。
```

MVP 验收样例仍以“央行降息 25bp + 平安银行重仓”为主。通过标准：

- 自动识别降息对银行的双刃剑逻辑。
- 能指出平安银行集中仓位是组合主要解释变量。
- 能区分政策利好、净息差压力、资产质量担忧、地产链修复。
- 每个关键判断都有证据或明确标记为假设。
- 沙盘解释不产生收益数字。
- 删除 `MiroFish` 文件夹后系统不受影响。

## 17. 风险与边界

必须长期遵守：

- LLM 不得生成收益区间。
- LLM 不得生成确定性买卖指令。
- 外部证据必须保存来源、URL、抓取时间和质量分。
- 新闻热度不能直接等于投资影响。
- 沙盘涌现不能直接等于真实市场结果。
- 无正文、低质量或过期证据必须降权。
- 免费聚合源失败不能阻塞本地压力测试。
- 所有 Agent 结论必须带证据或标注为假设。
- 图谱抽取出的因果边必须可审计、可删除、可回测。
- `MiroFish`、`TrendRadar` 均只能作为思想来源，不得成为运行依赖。

---

## 18. 最终目标

V2.1 的目标不是把 StockM1 做成一个“会讲故事的新闻总结器”，也不是把 MiroFish 式通用群体模拟直接搬到金融里。

真正的新高度是：

```text
可审计事实
  支撑
可计算压力测试
  约束
金融主体沙盘解释
  最终输出
普通投资者能理解、专业用户能复核、历史回测能检验的情景推演报告
```

这样，StockM1 Scenario Lab 才能从“本地数据压力测试工具”升级为“金融背景下的证据驱动、图谱增强、多 Agent 可解释情景推演实验室”。
