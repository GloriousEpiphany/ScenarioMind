# 情景推演实验室改进 V2：全网数据收集、Agent 深度分析与可解释报告方案

## 1. 当前问题

现有情景推演实验室已经能做本地价格数据压力测试、规则化情景解析、确定性 Agent 审查和普通投资者版摘要，但它仍然不是完整的“联网研究 Agent”。

典型问题是：

> 在“降息 25bp”情景下，报告只给出组合回报区间、低数据置信度、缺失信息等，并不能主动收集央行政策、市场预期、银行板块新闻、平安银行基本面、历史降息窗口和最新舆情。

这说明当前系统缺少以下能力：

- 主动规划需要查什么数据。
- 从全网、RSS、热榜、公告、政策源、财经源收集证据。
- 对证据做去重、时间排序、热度追踪、正文读取和质量评分。
- 将证据接入 RAG / 知识图谱 / Agent 辩论。
- 用普通投资者能理解的话给出结论、风险触发条件和候选动作。

## 2. 对 TrendRadar 数据收集方法的评估

本方案参考 `TrendRadar` 文件夹中的实现方法，但不会在 StockM1 中直接 `import TrendRadar` 代码。`TrendRadar` 后续可删除；需要使用的方法会在 StockM1 内重新实现。

### 2.1 TrendRadar 的核心方法

TrendRadar 的数据能力主要包括：

- 通过 NewsNow API 抓取多平台热榜。
- 通过 RSS 抓取订阅源文章。
- 使用请求重试、随机间隔、代理配置、超时控制。
- 使用 SQLite 存储新闻条目、平台、抓取记录、来源状态、排名历史。
- 用 URL + 来源去重，RSS 中用 guid + feed_id 优先去重。
- 记录 first_crawl_time、last_crawl_time、crawl_count、rank_history。
- 支持 daily / current / incremental 三种报告模式。
- 支持关键词搜索、模糊搜索、实体搜索、历史相关新闻搜索。
- 支持 AI 兴趣标签提取、批量标题分类、相关性打分。
- 通过 Jina Reader 将 URL 转换为 Markdown 正文，供 LLM 阅读。
- 支持 AI 对多源热点进行综合分析。

### 2.2 是否是“最好用”的方法

结论：TrendRadar 的方法适合做“全网热点与舆情雷达”，但不是金融情景推演的完整最优方案。

它的优点：

- 对热点捕捉很强，能发现市场正在讨论什么。
- 热榜 + RSS 双通道比单一新闻 API 更稳。
- 增量检测、排名轨迹、出现次数非常适合判断舆情热度变化。
- SQLite 本地证据库简单可靠，便于审计和复盘。
- AI 分类可以把海量标题过滤成与用户情景和持仓相关的新闻。
- Jina Reader 读取正文的方法适合低成本补全文本证据。

它的不足：

- NewsNow 热榜不是金融专业数据源，存在娱乐、社会、泛科技内容噪音。
- 热榜标题不能替代央行公告、交易所公告、上市公司公告、财报、行情和宏观数据。
- 热度不等于投资影响，必须经过金融事件分类和因果分析。
- 只有标题和排名不足以支撑严肃投资结论，需要正文、来源质量、发布时间和可追溯 URL。
- 免费聚合 API 的稳定性、合规性和覆盖范围需要兜底。

因此，TrendRadar 的最佳定位是：

> 作为 StockM1 情景推演实验室的“外部事件与舆情收集层”，而不是替代金融数据和量化压力测试引擎。

## 3. V2 总体目标

V2 的目标是把情景推演实验室升级为：

```text
用户情景 + 用户持仓
  -> 情景解析 Agent
  -> 研究规划 Agent
  -> 多源数据收集
  -> 证据入库与去重
  -> RAG / 知识图谱检索
  -> 多 Agent 分析与辩论
  -> 量化压力测试
  -> 普通投资者可读报告
```

最终报告必须回答：

- 这件事对我的持仓是偏利好、偏利空，还是不确定？
- 为什么？
- 证据来自哪里？
- 哪只持仓风险最大？
- 哪些条件会让结论反转？
- 我现在应该观察什么？
- 是否需要调仓，或者只是等待确认？

```python
@dataclass
class ExternalEvidenceDocument:
```

### 4.3 SQLite 证据库

参考 TrendRadar 的 SQLite 思路，但表结构要改为金融情景证据库：

```sql
CREATE TABLE IF NOT EXISTS scenario_external_sources (
    source_id TEXT PRIMARY KEY,
    source_name TEXT NOT NULL,
    source_type TEXT NOT NULL,
    endpoint TEXT DEFAULT '',
    is_active INTEGER DEFAULT 1,
    source_quality_score REAL DEFAULT 0.5,
    updated_at TEXT
);

CREATE TABLE IF NOT EXISTS scenario_external_evidence (
    evidence_id TEXT PRIMARY KEY,
    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL,
    title TEXT NOT NULL,
    url TEXT DEFAULT '',
    guid TEXT DEFAULT '',
    published_at TEXT DEFAULT '',
    first_seen_at TEXT NOT NULL,
    last_seen_at TEXT NOT NULL,
    crawl_count INTEGER DEFAULT 1,
    rank INTEGER,
    summary TEXT DEFAULT '',
    content_markdown TEXT DEFAULT '',
    entities_json TEXT DEFAULT '[]',
    event_tags_json TEXT DEFAULT '[]',
    related_symbols_json TEXT DEFAULT '[]',
    relevance_score REAL DEFAULT 0,
    source_quality_score REAL DEFAULT 0,
    freshness_score REAL DEFAULT 0,
    evidence_score REAL DEFAULT 0,
    metadata_json TEXT DEFAULT '{}',
    created_at TEXT,
    updated_at TEXT
);

CREATE TABLE IF NOT EXISTS scenario_external_rank_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    evidence_id TEXT NOT NULL,
    rank INTEGER,
    seen_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS scenario_external_crawl_runs (
    crawl_id TEXT PRIMARY KEY,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    query_context_json TEXT DEFAULT '{}',
    total_items INTEGER DEFAULT 0,
    success_count INTEGER DEFAULT 0,
    failed_count INTEGER DEFAULT 0
);

CREATE TABLE IF NOT EXISTS scenario_external_source_status (
    crawl_id TEXT NOT NULL,
    source_id TEXT NOT NULL,
    status TEXT NOT NULL,
    error_message TEXT DEFAULT '',
    item_count INTEGER DEFAULT 0,
    PRIMARY KEY (crawl_id, source_id)
);
```

去重策略：

- 热榜/新闻：优先 `url + source_id`。
- RSS：优先 `guid + source_id`，没有 guid 时用 `url + source_id`。
- 无 URL 时用 `sha1(title + source_id + published_at)`。
- 同一标题多次出现时更新 `last_seen_at`、`crawl_count`、`rank_history`。

### 4.4 增量与热度轨迹

保留 TrendRadar 的重要思想：

- `first_seen_at`：第一次被发现。
- `last_seen_at`：最后一次出现。
- `crawl_count`：出现次数。
- `rank_history`：排名轨迹。
- `new_items`：本轮新增证据。

在情景推演中，这些字段用于判断：

- 事件是突发还是持续发酵。
- 舆情是否升温。
- 是否跨多个平台传播。
- 是否只是一次性噪音。

热度分数示例：

```text
hotness_score =
  0.35 * 来源质量
+ 0.25 * 排名分
+ 0.20 * 出现次数分
+ 0.10 * 跨平台覆盖
+ 0.10 * 新鲜度
```

### 4.5 AI 兴趣分类迁移为“情景相关性分类”

TrendRadar 的 AI 兴趣分类应改造为金融情景分类。

输入不再是 `ai_interests.txt`，而是：

- 用户情景。
- 结构化冲击因子。
- 持仓股票。
- 相关行业。
- 当前分析目标。

标签由系统自动生成：

```text
降息情景示例标签：
- 央行政策信号
- LPR/MLF/OMO 利率变化
- 银行净息差
- 宽信用与社融
- 地产链修复
- 银行股估值修复
- 风险偏好变化
- 平安银行相关公告/新闻
```

AI 分类输出：

```json
[
  {
    "evidence_id": "xxx",
    "tag": "银行净息差",
    "relevance_score": 0.86,
    "reason": "标题和正文讨论降息对银行息差压力的影响"
  }
]
```

### 4.6 正文读取

参考 TrendRadar 的 Jina Reader 方法，但在 StockM1 中重新实现 `ArticleContentReader`。

读取策略：

- 默认只读取高分证据的正文，避免成本和限流。
- 单轮最多读取 5-10 篇。
- 请求间隔 3-5 秒。
- 失败时保留标题级证据，但降低证据分。
- 正文存入 `content_markdown`。

优先读取：

- 央行/交易所/公司公告。
- 财经媒体深度报道。
- 与持仓直接相关的新闻。
- 跨平台高热度新闻。

## 5. 金融垂直数据源设计

TrendRadar 的热榜/RSS 只是外部舆情层。金融情景推演还必须增加垂直数据源。

### 5.1 政策与宏观源

优先级最高：

- 中国人民银行公告、货币政策工具、公开市场操作。
- 全国银行间同业拆借中心 LPR。
- 国家统计局 CPI/PPI/PMI。
- 财政部政策。
- 外汇交易中心人民币汇率。
- 中债/国债收益率曲线，若本地无正式源可先使用可审计代理数据。

### 5.2 市场与行情源

- 已有 `stock_daily`、`index_daily`。
- 新增行业指数、ETF、债券、汇率、商品代理。
- 对降息情景至少需要：
  - 沪深300。
  - 中证银行/申万银行指数。
  - 国债收益率代理。
  - 房地产指数。
  - 成长风格指数。

### 5.3 公告与公司源

- 巨潮资讯公告。
- 上交所、深交所公告。
- 公司财报。
- 对持仓公司提取：
  - 主营业务。
  - 行业分类。
  - 关键财务指标。
  - 对宏观因子的暴露。

### 5.4 新闻与舆情源

可迁移 TrendRadar 风格的数据源：

- 财联社热榜。
- 华尔街见闻热榜。
- 澎湃、凤凰、微博、知乎等泛舆情。
- Yahoo Finance RSS。
- 自定义财经 RSS。

但必须加金融白名单和来源质量评分，避免泛娱乐内容污染投资报告。

## 6. Agent 算法设计

### 6.1 Research Planner Agent

输入：

- `ScenarioSpec`
- `PortfolioSnapshot`
- 用户亏损阈值
- 分析深度

输出：

```json
{
  "research_questions": [
    "本次降息是否已发生还是假设？",
    "市场是否已提前定价？",
    "银行股历史上如何反应？",
    "平安银行对净息差和地产链暴露如何？"
  ],
  "queries": [
    "央行 降息 25bp LPR MLF",
    "平安银行 净息差 降息",
    "银行股 降息 影响",
    "LPR 下调 银行 净息差"
  ],
  "required_sources": ["policy", "market", "hotlist", "rss", "announcement"],
  "article_reading_budget": 8
}
```

### 6.2 Data Collection Agents

按来源拆分：

- `PolicyCollectorAgent`
- `MarketDataAgent`
- `HotlistCollectorAgent`
- `RSSCollectorAgent`
- `AnnouncementCollectorAgent`
- `ArticleReaderAgent`

每个 Agent 都必须返回：

- 成功/失败状态。
- 证据条数。
- 来源状态。
- 错误原因。
- 数据边界。

### 6.3 Evidence Normalizer Agent

负责：

- 标题清洗。
- URL 规范化。
- 发布时间标准化。
- 实体抽取。
- 事件标签抽取。
- 股票代码映射。
- 证据质量评分。

### 6.4 RAG Retrieval Agent

检索逻辑：

- 关键词检索：适合精确政策词。
- 模糊检索：适合历史相关新闻。
- 实体检索：适合持仓公司。
- 向量检索：适合正文语义匹配。
- 图谱检索：适合因果链推理。

### 6.5 Debate Agents

对报告结论做多角色审查：

- `Bull Agent`：寻找正面传导路径。
- `Bear Agent`：寻找负面传导路径。
- `Risk Agent`：寻找组合脆弱点。
- `Evidence Critic Agent`：检查证据是否过期、来源是否低质、是否存在反证。
- `Retail Report Agent`：检查普通投资者是否能读懂。

输出必须带 `evidence_id`，不能空口判断。

## 7. 量化分析算法

### 7.1 历史事件类比

以降息 25bp 为例，系统应自动构建历史窗口：

- LPR 下调。
- MLF 下调。
- 存款利率下调。
- 降准。
- 宽信用政策组合。

对每个窗口计算：

- 事件后 1 周、1 月、3 月收益。
- 持仓个股收益。
- 行业指数收益。
- 相对沪深300超额收益。
- 事件前市场状态：估值、趋势、波动、信用周期。

### 7.2 因子暴露

新增因子：

- `market_beta`
- `interest_rate_beta`
- `credit_beta`
- `liquidity_beta`
- `bank_margin_beta`
- `real_estate_beta`
- `risk_appetite_beta`
- `news_hotness_beta`

### 7.3 证据修正

量化区间仍由确定性模型生成，LLM 不得直接生成涨跌幅。

但外部证据可以调整：

- 置信度。
- 情景路径权重。
- 不确定性说明。
- 是否扩大区间。
- 是否触发“证据不足，不输出强结论”。

示例：

```text
如果最新证据显示：
- 降息伴随存款利率下调，银行息差压力缓和；
- 地产政策同步放松；
- 银行板块热度上升；

则 Base/Bull 路径权重提高。

如果最新证据显示：
- 降息被市场解读为经济压力；
- 银行净息差继续下行；
- 平安银行资产质量担忧升温；

则 Bear 路径权重提高，并扩大下沿。
```

## 8. 报告生成方案

新版报告结构：

```text
1. 一句话结论
2. 行动判断：需要调仓 / 暂不行动 / 等待确认 / 证据不足
3. 对你的组合意味着什么
4. 最大风险持仓
5. 最大不确定性
6. 利好逻辑
7. 利空逻辑
8. 关键观察信号
9. 调仓/对冲候选方案
10. 证据链
11. Agent 审查记录
12. 审计与数据边界
```

降息报告示例口径：

```text
结论：降息 25bp 对你的组合不是简单利好。由于平安银行权重过高，核心矛盾是“流动性改善带来的估值修复”与“净息差压力”谁更强。若降息伴随存款利率下调、地产政策继续放松，银行股压力可能缓和；若只是因为经济压力被动降息，银行资产质量和息差担忧可能压制表现。
```

必须避免：

- 只展示专业指标。
- 只给收益区间。
- 用“置信度 40%”替代解释。
- 给出无证据买卖建议。

## 9. 与现有代码集成点

### 9.1 ScenarioEngine.run

当前流程：

```text
parse -> portfolio -> shocks -> constraints -> analogs -> factors -> simulate -> report
```

V2 改为：

```text
parse
-> portfolio
-> research_orchestrator.collect()
-> evidence normalization
-> RAG / graph enrich
-> shocks / constraints / analogs / factors
-> evidence-adjusted simulation
-> multi-agent review
-> retail report
```

伪代码：

```python
research_bundle = self.research_orchestrator.collect(
    spec=spec,
    portfolio=portfolio,
    mode=mode,
    as_of_date=as_of_date,
)

external_evidence = self.evidence_adapter.to_scenario_evidence(research_bundle.documents)
evidence += external_evidence

research_context = self.rag_retriever.retrieve(
    query=spec.user_query,
    symbols=[p.symbol for p in portfolio.positions],
    top_k=20,
)

impacts, total_impact, paths = self.simulator.simulate(
    spec=spec,
    portfolio=portfolio,
    external_context=research_context,
)

report.audit["external_research"] = research_bundle.audit
report.audit["agent_research"] = research_bundle.agent_traces
```

- 高相关证据正文读取。

目标：

- 从大量新闻中筛出和持仓/情景真正相关的证据。

### Phase 4：Agent 研究编排

交付：

- `ResearchPlannerAgent`
- `PolicyAgent`
- `MarketAgent`
- `CompanyAgent`
- `NewsAgent`
- `EvidenceCriticAgent`

目标：

- 系统知道该查什么、为什么查、查到什么、哪些证据支持或反驳结论。

### Phase 5：接入量化与报告

交付：

- 外部证据修正置信度。
- 外部证据影响路径权重。
- 报告展示证据链和 Agent 结论。
- Streamlit 页面支持外部研究开关。

目标：

- 报告从“指标展示”升级为“证据驱动的投资者可读分析”。

## 11. MVP 建议

第一版不要一次做全量 Graph RAG 和所有金融源，建议先做最小闭环：

```text
1. 热榜 + RSS 采集
2. 财经源白名单
3. 证据 SQLite 入库
4. 情景相关性 AI 分类
5. 高分文章正文读取
6. Agent 生成普通投资者版结论
7. 报告引用 evidence_id
```

以“央行降息 25bp + 平安银行重仓”为验收样例。

通过标准：

- 系统自动查到央行/LPR/银行/平安银行/银行板块相关新闻。
- 能区分“降息利好流动性”和“压缩银行净息差”两条相反逻辑。
- 能指出平安银行重仓导致组合对银行板块解释高度敏感。
- 能给出普通投资者可理解结论。
- 每个关键判断都有证据来源。
- 没有证据时明确说“不足以判断”，而不是编造结论。

## 12. 风险与边界

必须遵守：

- LLM 不得生成收益区间。
- LLM 不得生成确定性买卖指令。
- 外部证据必须保存来源、URL、抓取时间。
- 新闻热度不能直接等于投资结论。
- 没有正文或来源质量低的证据应降低权重。
- 免费聚合 API 失败时不能阻塞本地压力测试。
- 删除 `TrendRadar` 文件夹后，StockM1 仍必须独立运行。

## 13. 最终结论

TrendRadar 的数据收集方法值得集成，但应被改造为 StockM1 的“外部研究证据层”。

最佳集成方式不是直接复制一个热点新闻产品，而是吸收它的工程方法：

- 多源抓取。
- RSS 支持。
- 增量去重。
- 排名轨迹。
- SQLite 审计存储。
- AI 批量分类。
- 正文读取。
- 搜索与历史相关检索。

再叠加 StockM1 必需的金融专业源、持仓映射、因子模型和 Agent 审查，形成完整的情景推演 V2。

这样系统才能从当前的“本地数据压力测试工具”，升级为“能主动收集证据、解释影响路径、给普通投资者结论的 Agent 研究实验室”。
